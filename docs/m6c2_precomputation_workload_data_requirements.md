## 3. Workload Data Definition
**ARCHITECTURAL CONSEQUENCE**: Workload data is defined exclusively as telemetry generated by actual application usage (e.g., API request payloads, user sessions, runtime optimization invocations). Scientific evidence records (M5 database) and synthetic test cases DO NOT constitute workload data.

## 4. Minimum Workload Record
**PROPOSED DESIGN**: A conceptual workload record requires the following field classifications:
- **REQUIRED**: Request ID, timestamp, request inputs (commodity, target shelf-life, temperature, RH, geometry), active objectives, candidate filter settings.
- **DERIVED**: Resolved Phase 4 requirement envelope, resolved candidate ID set, resulting canonical Optimization-State Identity.
- **OPTIONAL**: Session ID, client system ID.
- **NOT REQUIRED**: Individual user PII, payment info, IP addresses.

## 5. Raw Request vs Resolved State
**EXISTING FACT**: 
- **Raw User Request**: Captures the raw user inputs (`commodity`, `variety`, `storage_temperature_c`). Useful for analyzing user behavior and domain demand.
- **Resolved Optimization-State Identity**: Captures the resulting Phase 4 envelope, geometry, active objectives, and candidate ID set. Essential for mapping demand to actual precomputable states.
**SOURCE-AUTHORIZED REQUIREMENT**: Workload datasets MUST preserve both layers without turning raw requests into a second optimization identity system.

## 6. Mapping to Optimization-State Identity
**ARCHITECTURAL CONSEQUENCE**: To evaluate whether a workload record justifies precomputing a state, the workload record must be capable of executing Phase 3, Phase 4, and M6-B1 filtering to resolve the exact canonical Optimization-State Identity that would be queried at Tier-1 runtime.

## 7. Request Outcomes
**PROPOSED DESIGN**: A complete workload telemetry record should track runtime resolution outcomes:
- `EXACT_HIT` (Tier-1 fulfilled request)
- `EXACT_MISS` (Tier-1 cache miss)
- `TIER2_WARM_START` (Tier-2 seed selected and refined)
- `TIER3_COLD_OPTIMIZATION` (Cold optimization executed from scratch)
- `UNFEASIBLE_REQUEST` (Over-constrained Phase 4/5 result)

## 8. Frequency Semantics
**ARCHITECTURAL CONSEQUENCE**: "Demand frequency" can be analyzed across multiple dimensions:
- Raw request count per commodity/temperature.
- Unique Optimization-State Identity request count.
- Repeat request count for identical canonical identities.
- Target objective set popularity.

No weighting formulas or frequency thresholds are authorized.

## 9. Temporal Information
**UNRESOLVED**: WORKLOAD ANALYSIS TIME HORIZON NOT YET AUTHORIZED. The architecture does not define rolling window sizes (e.g., 7-day, 30-day, 90-day) or time decay factors for analyzing demand recency.

## 10. Population-Policy Inputs
**ARCHITECTURAL CONSEQUENCE**: If workload data is collected, the primary quantities available to inform future population policies are:
1. Canonical identity repeat request count.
2. Tier-1 miss frequency per identity domain.
3. Candidate search-space popularity.

## 11. Privacy / PII
**UNRESOLVED**: WORKLOAD PRIVACY POLICY NOT YET AUTHORIZED. Workload telemetry should strictly record technical request parameters rather than user PII. No legal compliance regime is defined.

## 12. Scientific Evidence Separation
**SOURCE-AUTHORIZED REQUIREMENT**: M5 experimental observations (respiration rates, permeability tests) describe scientific physical realities. They MUST NOT be used to infer user demand frequency, commodity popularity, or workload probability.

## 13. Synthetic / Demo Data
**EXISTING FACT**: Synthetic test cases are valid for pipeline integration testing and benchmarking.
**SOURCE-AUTHORIZED REQUIREMENT**: Synthetic test scripts MUST NOT be conflated with real production workload evidence to justify precomputing states.

## 14. Data Quality Requirements
**PROPOSED DESIGN**: Workload records must be structurally valid, complete, and reproducible through the Phase 3/4 pipeline to be eligible for workload analysis.

## 15. Representativeness
**UNRESOLVED**: WORKLOAD REPRESENTATIVENESS CRITERIA NOT YET AUTHORIZED. No statistical confidence levels or sample sizes are defined.

## 16. Minimum Viable Workload Dataset
**PROPOSED DESIGN**:
- **Basic Telemetry**: Timestamp, raw request fields, response status.
- **Optimization Mapping**: Resolved Phase 4 envelope, package geometry, active objectives, candidate ID set.
- **Tier Outcome**: Tier-1 Hit/Miss flag, solver execution time.
