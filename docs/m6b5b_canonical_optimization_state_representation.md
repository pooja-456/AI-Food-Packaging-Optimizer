# M6-B5B Canonical Optimization-State Representation

## 1. Status
**PROPOSED DESIGN — AWAITING REVIEW**

## 2. Source Basis
**EXISTING FACT**: This contract relies directly on:
- `m6a_optimization_state_identity_contract.md`
- `m6a_tier1_addressability_contract.md`
- `m6b5a_precomputed_state_store_contract.md`
- M6-B1 optimization schemas (`OptimizationInputEnvelope`, `PackageGeometry`, `ObjectiveValue`)
- Phase 4 physics schemas (`PackagingRequirementEnvelope`, `ScientificResult`, `GasExchangeRequirement`, `MoistureRequirement`)
- Phase 5 feasibility schemas (`FilteringResult`, `CandidateFeasibility`)

## 3. Frozen Optimization Identity
**SOURCE-AUTHORIZED REQUIREMENT**: The canonical representation MUST represent the four frozen identity components and NO OTHERS:
1. Phase 4 `PackagingRequirementEnvelope`
2. `PackageGeometry`
3. `active_objectives` (unordered set)
4. `eligible_candidate_materials` (unordered set of Candidate IDs)

Excluded metadata (raw commodity context, variety, ripeness, evidence tier, provenance, inference traces, filtering rationale) MUST NOT enter the representation.

## 4. Canonical Representation Requirements
**SOURCE-AUTHORIZED REQUIREMENT**: The representation must satisfy:
- **Determinism**: Identical identity values map to identical representations.
- **Distinguishability**: Non-identical identities map to distinct representations.
- **Order Invariance**: Reordering active objectives or candidate IDs does NOT alter representation.
- **Interval Preservation**: Lower/upper bounds and range flags must remain explicit.
- **UNKNOWN Preservation**: `UNKNOWN` status must not be converted into zero, null, or empty defaults.

## 5. Phase 4 Requirement Envelope Representation
**EXISTING FACT**: `PackagingRequirementEnvelope` contains:
- Primary environmental scalars (`storage_temperature_c`, `relative_humidity_percent`, `target_shelf_life_days`).
- Requirement profiles (`gas_requirements`, `moisture_requirements`, `microbial_requirements`, `shelf_life_requirement`, `deterioration_profile`).
- Target fields contain `ScientificResult` objects (housing `value`, `value_min`, `value_max`, `unit`, `is_range`, `status`, `operator`).

**PROPOSED DESIGN**: Each present requirement field is mapped as a discrete structured record holding its numeric values/bounds, unit string, comparison operator, and status enum.

## 6. Interval Representation
**SOURCE-AUTHORIZED REQUIREMENT**: A non-degenerate interval (`value_min < value_max`) MUST be explicitly represented with both its lower bound and upper bound alongside `is_range=True`. Collapsing an interval to a scalar midpoint is strictly prohibited.

## 7. UNKNOWN Representation
**SOURCE-AUTHORIZED REQUIREMENT**: A field carrying `status=CalculationStatus.UNKNOWN` MUST be canonically represented with its explicit `UNKNOWN` status marker. It MUST NOT be converted into `0.0`, `None`, or omitted.

## 8. Package Geometry Representation
**EXISTING FACT**: `PackageGeometry` has three mandatory scalar fields:
- `surface_area_m2` (float)
- `headspace_volume_cm3` (float)
- `product_mass_kg` (float)

**PROPOSED DESIGN**: Preserved as explicit key-value scalar entries within the canonical structure.

## 9. Active Objective Set Representation
**EXISTING FACT**: `active_objectives` is a `List[str]` representing an unordered mathematical set of objective identifiers (e.g., `["shelf_life_margin", "material_cost"]`).

**PROPOSED DESIGN**: To guarantee order invariance semantically, the canonical representation requires that active objectives are evaluated as an unordered set (or lexicographically sorted unique sequence during canonical serialization).

## 10. Candidate ID Set Representation
**EXISTING FACT**: `eligible_candidate_materials` in M6-B1 is a `List[PackagingCandidate]`. Each candidate has a deterministic UUID string `candidate_id` generated by `CandidateBuilder`.

**PROPOSED DESIGN**: The search space identity requires ONLY the set of candidate IDs (`List[str]`), not the full nested candidate objects. The canonical representation requires treating candidate IDs as an unordered set (or lexicographically sorted unique sequence of ID strings).

## 11. Optional / Missing Field Semantics
**EXISTING FACT**: In Phase 4 requirements:
- `None` (absent field) = No requirement was specified for this parameter.
- `ScientificResult(status=UNKNOWN)` = A requirement was evaluated but failed to yield a deterministic bound.

**SOURCE-AUTHORIZED REQUIREMENT**: `None` and `UNKNOWN` have fundamentally distinct scientific and optimization meanings. The canonical representation MUST preserve `ABSENT` vs `UNKNOWN` as distinct states.

## 12. Floating-Point Semantics
**EXISTING FACT**: Inspection of backend schemas (`PackagingRequirementEnvelope`, `PackageGeometry`) reveals that Python standard `float` is used throughout. No rounding (`round()`), `Decimal` truncation, or `math.isclose()` tolerance is currently authorized in the scientific engine.

**UNRESOLVED**: FLOATING-POINT CANONICALIZATION NOT YET AUTHORIZED. The existing architecture uses raw floating-point values. Introducing arbitrary rounding (e.g., `round(val, 4)`) or float-to-string formatting rules without scientific tolerance authorization is prohibited. IEEE 754 float representation subtleties are deferred to M6-B5C implementation design.

## 13. Unit Semantics
**EXISTING FACT**: Scientific metrics include `unit` strings (e.g., `cc/m2/day`, `g/pkg/day`). Phase 4 outputs standard canonical unit strings per metric type.

**PROPOSED DESIGN**: The canonical representation MUST include the `unit` string alongside every numerical value/interval to prevent cross-unit ambiguity.

## 14. Version / Validity Separation
**EXISTING FACT**: Per Decision #3A and M6-B5A, `constraint_policy_version` and solver metadata are metadata fields.

**SOURCE-AUTHORIZED REQUIREMENT**: Versioning metadata is strictly separated from the Optimization-State Identity. It does not enter the canonical identity representation.

## 15. Canonical Representation vs Hash / Key
**ARCHITECTURAL CONSEQUENCE**: The **Canonical Representation** is a deterministic, structured data object (e.g., a canonical key-value tree) representing the identity. The **Hash / Key** is the output of a cryptographic hashing algorithm (e.g., SHA-256) applied to that serialized representation. M6-B5B defines the Canonical Representation only; selecting a hash algorithm is deferred to M6-B5C.

## 16. Collision and Distinguishability Requirements
**SOURCE-AUTHORIZED REQUIREMENT**: Two non-identical Optimization-State Identities MUST produce distinct canonical representations prior to any hashing step. Hashing MUST NOT be relied upon to resolve ambiguity that exists in the canonical structure itself.

## 17. Round-Trip Semantics
**UNRESOLVED**: ROUND-TRIP RECONSTRUCTION NOT AUTHORIZED. The current architecture requires that an identity generates a unique, deterministic canonical representation for lookup. It does NOT require that the original full Phase 4 Pydantic model objects be reconstructible solely from the canonical representation key.

## 18. Explicitly Deferred Decisions
The following physical choices are explicitly deferred to M6-B5C / implementation:
- Cryptographic hash algorithm (SHA-256, BLAKE3, etc.).
- String serialization format (Canonical JSON, Protocol Buffers, MessagePack).
- Floating-point string formatting rules (e.g., ryu, Grisu3, or standard IEEE repr).
- Physical storage engine (Redis, PostgreSQL, memory dict).
- Cache key string prefixing/namespacing.

## 19. M6-B5C Readiness
**ARCHITECTURAL CONSEQUENCE**: READY. The Canonical Optimization-State Representation Contract is complete. All identity fields, set-ordering constraints, interval preservation rules, and UNKNOWN/ABSENT distinctions are defined. M6-B5C may proceed to design the concrete hashing and key-generation mechanics.
