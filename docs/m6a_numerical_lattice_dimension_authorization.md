# M6-A Numerical Lattice Dimension Authorization

## 1. Status
**PROPOSED DECISION — AWAITING REVIEW**

## 2. Architectural Question
"Which existing scalar numerical dimensions are authorized to become future lattice coordinates, without selecting numerical resolutions, domains, or rounding rules?"

## 3. Candidate Numerical Dimensions
**EXISTING FACT**: The optimization-state identity surfaces the following candidate numerical fields:
- `target_shelf_life_days`
- `storage_temperature_c`
- `relative_humidity_percent`
- `surface_area_m2`
- `headspace_volume_cm3`
- `product_mass_kg`
- Required OTR (`gas_requirements.required_otr_cc_per_pkg_day`)
- Required CO2TR (`gas_requirements.required_co2tr_cc_per_pkg_day`)
- Required WVTR (`moisture_requirements.required_wvtr_g_per_pkg_day`)

## 4. Target Shelf-Life Analysis
**EXISTING FACT**: `target_shelf_life_days` is a PRIMARY user input. It is a strictly scalar numerical value. It directly drives Phase 4 deterioration accumulation, Phase 5 feasibility limits, and M6-B3 shelf-life margin objectives. 
**ARCHITECTURAL CONSEQUENCE**: It is completely eligible for scalar lattice coordinate discretization.

## 5. Temperature Analysis
**EXISTING FACT**: `storage_temperature_c` is a PRIMARY user input. It is a strictly scalar numerical float. It directly governs Phase 4 thermodynamic shifts (e.g., respiration Q10, vapor pressure) and Phase 5 environmental condition matching.
**ARCHITECTURAL CONSEQUENCE**: It is completely eligible for scalar lattice coordinate discretization.

## 6. Relative-Humidity Analysis
**EXISTING FACT**: `relative_humidity_percent` is a PRIMARY user input. It is a strictly scalar numerical float. It directly governs Phase 4 moisture flux limits and Phase 5 environmental condition matching.
**ARCHITECTURAL CONSEQUENCE**: It is completely eligible for scalar lattice coordinate discretization.

## 7. Barrier Requirement Analysis
**EXISTING FACT**: Required OTR, CO2TR, and WVTR are DERIVED SCIENTIFIC OUTPUTS. They are physically generated by the mathematical models in Phase 4.
**ARCHITECTURAL CONSEQUENCE**: Because they natively contain biological uncertainty (`value_min`, `value_max`), they are strictly interval-valued constraints within the optimization engine, not scalar bounds. 
**PROPOSED DECISION**: As interval-valued outputs, they are explicitly NOT currently authorized to act as scalar lattice coordinates (per M6-A Decision #2B). Attempting to discretize them as scalars fundamentally breaks Pareto dominance mechanics.

## 8. Package Geometry Analysis
**EXISTING FACT**: `surface_area_m2`, `headspace_volume_cm3`, and `product_mass_kg` are PRIMARY user inputs. They are strictly scalar numerical floats. They independently scale the required package-level transmission rates and influence the M6-B2B candidate recalculation phase.
**ARCHITECTURAL CONSEQUENCE**: They are eligible for scalar lattice discretization.

## 9. Primary vs Derived Dimensions
**PROPOSED DECISION**: To efficiently index the lattice without requiring unresolved multi-dimensional interval hashing, the caching key should mathematically prioritize the PRIMARY scalar inputs (`target_shelf_life_days`, `storage_temperature_c`, `relative_humidity_percent`, `PackageGeometry`) rather than the DERIVED interval outputs (`required_otr`, `required_wvtr`).
**UNRESOLVED**: While primary inputs are scalar and cacheable, using them resurrects the exact "Food Context / Biological State" caching fragmentation problem identified in Decision #1A (since the primary inputs do not uniquely define the biological traits without the raw `commodity` or resolved traits). The architecture has not resolved how to bridge primary-input caching with abstract biological states.

## 10. Interval Exclusion
**SOURCE-AUTHORIZED REQUIREMENT**: A non-degenerate interval MUST NOT be treated as a scalar lattice coordinate. The derived barrier requirements (`OTR`, `CO2TR`, `WVTR`) are strictly interval-valued limits, and the architecture explicitly prohibits arbitrary interval-to-scalar compression (e.g., midpoints).

## 11. Categorical / Set Dimensions
**EXISTING FACT**: The **Active Objective Set** and **Eligible Candidate ID Set** remain strictly non-numerical, unordered mathematical sets. They cannot be dimensionally discretized into continuous numerical coordinates. They represent independent indexing namespaces.

## 13. Computational Discretization vs Scientific Equivalence
**SOURCE-AUTHORIZED REQUIREMENT**: Approving a dimension as "Lattice Eligible" merely establishes that the field *can* mathematically participate in a caching hash key. It absolutely does NOT authorize scientific equivalence. Grouping a geometric area of `0.10 m2` and `0.11 m2` into a single lattice bin does not magically render them physically identical; it only dictates that they will retrieve the same precomputed Pareto front. The original continuous precision must persist in the trace.

## 14. Authorized Decisions
- The primary environmental inputs (`shelf_life`, `temp`, `rh`) are authorized for scalar discretization.
- The primary geometric inputs (`area`, `headspace`, `mass`) are authorized for scalar discretization.
- The derived barrier interval outputs (`OTR`, `CO2TR`, `WVTR`) are explicitly excluded from scalar discretization.

## 15. Unresolved Decisions
- The numerical sizing, resolutions, tolerances, boundaries, and domain handling for the authorized scalar dimensions remain fully unresolved.
- Indexing the lattice purely by primary scalar inputs + string identifiers (Commodity) ignores the fallback unification problem outlined in Decision #1A, exposing a severe architectural contradiction.

## 16. M6-B5 Gating Consequence
**EXISTING FACT**: M6-B5 remains strictly BLOCKED. The numerical discretization rules cannot proceed until the contradiction between the "Phase 4 Envelope Identity" (which contains un-cacheable intervals) and the "Primary Scalar Inputs" (which fragments the cache) is formally reconciled by the architecture board.
